# Вимоги до фронтенду: повне використання можливостей бекенду

Цей документ описує, що потрібно реалізувати на фронті, щоб задіяти всі
ендпоінти `f1-predictor-backend`. Для кожного ендпоінта: URL, параметри,
форма відповіді (реальні поля, отримані живим тестуванням) і що саме має
з'явитись в UI, щоб ця відповідь була використана, а не просто отримана.

Базова адреса бекенду задається через env (`VITE_API_URL` / аналог) —
хардкодити `localhost:8000` у фронті не варто, бекенд уже підтримує
`FRONTEND_ORIGIN` для CORS з іншого боку.

---

## 0. Наскрізні вимоги (стосуються всіх екранів)

1. **Ієрархічна навігація рік → етап → сесія → (результати | пілот | порівняння)**.
   Жоден ендпоінт даних (results/laps/driver/compare/weather) не працює без
   `year` + `round_number` + `session` — фронт має провести користувача
   через явний вибір усіх трьох, а не просити вручну вводити номер етапу.
2. **Список сесій береться з `/api/sessions`, не хардкодиться.** Набір
   сесій відрізняється: на звичайному вікенді це FP1/FP2/FP3/Q/R, на
   спринтерському — FP1/SQ/S/Q/R (без FP2/FP3). Якщо зашити список сесій
   на фронті, спринтерські вікенди будуть показувати неіснуючі FP2/FP3 і
   ловити 404 на них.
3. **Коди пілотів (`VER`, `HAM`, ...) для `/api/driver`, `/api/laps`,
   `/api/compare` мають братись з `/api/drivers`**, а не вводитись
   вручну текстовим полем — інакше typo дає 404/порожній результат без
   explaination для користувача.
4. **Обробка помилок бекенду.** Усі помилки повертаються як
   `{"detail": "..."}` з кодом `400` (некоректний запит, напр. менше
   2 пілотів у `/api/compare`) або `404` (сезон/етап/сесія/пілот не
   знайдені чи дані відсутні). Фронт має показувати `detail` користувачу,
   а не generic "Сталася помилка".
5. **Довгі перші запити, кеш лише на бекенді.** Бекенд кешує на диску
   (`cache/fastf1_http_cache.sqlite`) тільки сирий фід від FastF1 —
   перший запит по (year, round, session) тягне дані з зовнішнього
   джерела й повільний, повторний запит по тій самій сесії бере кеш і
   швидкий. Але це кеш **на сервері**, не в браузері: кожен HTTP-запит
   з фронту все одно йде мережею й наново серіалізується бекендом,
   навіть якщо там уже все закешовано. На фронті кешу відповідей немає
   зовсім — варто додати клієнтський data-кеш (напр. TanStack Query/SWR)
   з ключем `[year, round, session, endpoint]`, щоб не рефетчити при
   поверненні на вже відвідану сторінку (Результати ↔ Пілот ↔ Порівняння)
   в межах однієї сесії користувача. Плюс skeleton/spinner стани й,
   бажано, таймаут запиту суттєво більший за дефолтний (10+ секунд) —
   саме на перший, ще не закешований на бекенді, запит.
6. **`null` — очікуване значення, а не помилка.** Багато полів залежать
   від типу сесії й доступності даних (див. таблиці нижче) і легітимно
   приходять `null`. UI має рендерити прочерк/"—", а не ламатись чи
   ховати весь рядок.
7. **Час — число секунд (float), не рядок.** Усі часові поля (`LapTime`,
   `Sector1Time`, `Q1`/`Q2`/`Q3`, `Time` у результатах тощо) віддаються
   як кількість секунд (`93.66` = 1:33.660), щоб зручно сортувати й
   порівнювати. **Фронт сам відповідає за форматування** в `м:сс.мс`
   (і за формат "+0.421" для відставання, якщо будете рахувати дельти).

## 1. `GET /api/races/{year}` — календар сезону

Відповідь — масив етапів:

```
RoundNumber, EventName, OfficialEventName, Country, Location,
EventDate, EventFormat,
Session1..Session5 (назва), Session1DateUtc..Session5DateUtc
```

`EventFormat` ∈ `conventional` (звичайний вікенд) | `sprint_qualifying`
(сучасний формат спринту) | інші історичні значення.

**Потрібно на фронті:**
- Сторінка "Сезон {year}" зі списком/таблицею етапів (можна карточками
  по `Location`/`Country`), з вибором року (селектор або `/year/2018`…
  поточний рік у роуті).
- Візуальне маркування спринт-вікендів (бейдж "Sprint") на основі
  `EventFormat`, бо в них інша кількість сесій.
- Клік по етапу → перехід на сторінку етапу, яка одразу тягне
  `/api/sessions/{year}/{round}` (розділ 2).
- `EventDate` і `SessionXDateUtc` — ISO-рядки, конвертувати в локальний
  час користувача на фронті (`Date` + `Intl.DateTimeFormat`), бекенд
  часовий пояс не підбирає.

---

## 2. `GET /api/sessions/{year}/{round}` — сесії етапу

Відповідь — масив:

```json
[{"number": 1, "name": "Practice 1", "code": "FP1",
  "date": "2024-04-19T11:30:00+08:00", "date_utc": "2024-04-19T03:30:00"}, ...]
```

**Потрібно на фронті:**
- Сторінка етапу: таб-бар або список сесій, побудований **динамічно**
  з цієї відповіді (не хардкоджений `["FP1","FP2","FP3","Q","R"]`).
- Кожна сесія — клікабельна, `code` підставляється як `{session}` у всі
  наступні запити (results/drivers/laps/driver/compare/weather).
- Сесії, дата яких у майбутньому відносно поточного часу, мають бути
  задизейблені або показувати "ще не відбулась" замість спроби завантажити
  результати (бекенд поверне 404/порожні дані, а не помилку "рано питати").

---

## 3. `GET /api/results/{year}/{round}` та `/api/results/{year}/{round}/{session}`

Перший — скорочення для гонки (`session=R`), другий — будь-яка сесія.
Відповідь — масив пілотів, поля (усі присутні завжди, заповненість
залежить від сесії):

| Поле | Опис | Коли `null`/порожнє |
|---|---|---|
| `DriverNumber`, `Abbreviation`, `FullName`, `FirstName`, `LastName`, `BroadcastName`, `DriverId`, `CountryCode` | ідентифікація пілота | — |
| `TeamName`, `TeamId`, `TeamColor` (hex без `#`) | команда | — |
| `HeadshotUrl` | фото пілота | буває недоступне для старих сезонів |
| `Position`, `ClassifiedPosition` | підсумкова позиція (`ClassifiedPosition` — рядок, може бути `"R"`/`"D"`/`"W"` для сходу/дискваліфікації) | — |
| `GridPosition` | стартова решітка | `null` у практиках/кваліфікації |
| `Q1`, `Q2`, `Q3` | час кваліфікаційних сегментів (сек.) | `null` поза кваліфікацією/спринт-кваліфікацією |
| `Time` | загальний час/відставання від лідера (сек.) | `null` поза гонкою/спринтом |
| `Status` | `"Finished"`, `"+1 Lap"`, `"Retired"` тощо | порожній рядок поза гонкою/спринтом |
| `Points` | очки | `null` поза гонкою/спринтом |
| `Laps` | кількість пройдених кіл | `null` поза гонкою/спринтом |

**Потрібно на фронті:**
- Таблиця результатів з колонками, що **адаптуються під тип сесії**:
  для `Q`/`SQ` показувати колонки Q1/Q2/Q3 замість Points/Status/Time;
  для `R`/`S` — Points/Status/Time/Laps; для `FPx` — фактично лише
  позицію/найкращий темп (тут `Position` — умовний, орієнтуйтесь радше
  на `/api/laps` для практик, див. розділ 6).
- Колір рядка/бейджа команди з `TeamColor` (`background: #${TeamColor}`).
- Фото пілота з `HeadshotUrl` з фолбеком-заглушкою, якщо `null`.
- Клік на рядок пілота → перехід на `/api/driver/.../{driver}`
  (розділ 5), використовуючи `Abbreviation`.

---

## 4. `GET /api/drivers/{year}/{round}/{session}` — короткий список пілотів

Поля: `DriverNumber, Abbreviation, FullName, TeamName, TeamColor,
Position, GridPosition, Status, Points`.

**Потрібно на фронті:**
- Використати як джерело для **мультиселекту пілотів** у формах
  "Порівняти пілотів" і "Обрати пілота" — саме звідси беруться валідні
  `Abbreviation` для `/api/laps`, `/api/driver`, `/api/compare`
  (див. п. 0.3 — це закриває вимогу "не вводити коди руками").
- Компактний список/легенда з кольором команди для будь-якого графіка
  нижче (лапи, порівняння, погода-по-колах).

---

## 5. `GET /api/driver/{year}/{round}/{session}/{driver}` — сторінка пілота

Відповідь:

```json
{
  "driver": { ...ті самі поля, що в results... },
  "result": { ...рядок результату цього пілота (або null)... },
  "stints": [
    {"stint": 1.0, "compound": "MEDIUM", "laps": 13, "first_lap": 1.0, "last_lap": 13.0},
    ...
  ],
  "fastest_lap": { ...повний рядок кола (див. таблицю нижче)... } | null,
  "laps": [ ...усі кола пілота... ]
}
```

**Потрібно на фронті (окрема сторінка "Пілот у сесії", раніше не існувала):**
- Хедер: фото (`HeadshotUrl`), ім'я, команда з кольором, номер, країна
  (прапор за `CountryCode`).
- Блок підсумку: `result` (позиція/очки/статус — якщо не `null`) +
  `fastest_lap.LapTime` виділено окремо як "найшвидше коло сесії".
- **Стратегія шин**: горизонтальна смуга/timeline зі `stints` — кожен
  стінт як сегмент шириною `last_lap - first_lap + 1`, кольором за
  `compound` (SOFT/MEDIUM/HARD/INTERMEDIATE/WET — потрібна власна
  кольорова легенда компаундів, бекенд її не віддає).
- **Графік темпу**: `laps` → лінійний графік `LapNumber` (X) vs `LapTime`
  (Y, секунди → відформатувати як хв:сек), з маркуванням піт-стопів
  (`PitInTime`/`PitOutTime` не `null`) і `Deleted`-кіл (закреслені/сірі,
  видалені за `DeletedReason`).
- Таблиця всіх кіл з секторами (`Sector1Time/2/3`), швидкостями
  (`SpeedI1, SpeedI2, SpeedFL, SpeedST`), шиною (`Compound`, `TyreLife`,
  `FreshTyre`), позицією на колі (`Position`), прапорцем `IsPersonalBest`.
- Обробка 404 з текстом бекенду ("Пілот 'XXX' не знайдений у цій сесії"),
  якщо код пілота невалідний для обраної сесії.

## 6. `GET /api/laps/{year}/{round}/{session}?drivers=VER,HAM` — усі кола сесії

Без `drivers` — кола всіх пілотів (для гонки це може бути 1000+ рядків,
пагінація/віртуалізація таблиці — на розсуд фронта). Поля одного кола:

```
Time, Driver, DriverNumber, LapTime, LapNumber, Stint,
PitOutTime, PitInTime,
Sector1Time, Sector2Time, Sector3Time,
Sector1SessionTime, Sector2SessionTime, Sector3SessionTime,
SpeedI1, SpeedI2, SpeedFL, SpeedST,
IsPersonalBest, Compound, TyreLife, FreshTyre, Team,
LapStartTime, LapStartDate, TrackStatus,
Position, Deleted, DeletedReason, FastF1Generated, IsAccurate
```

**Потрібно на фронті:**
- Це основне джерело для **сторінок практик** (FP1–FP3), де `results`
  дає мало сенсу (немає очок/статусу) — там доречніша таблиця "найкраще
  коло кожного пілота" (мінімум `LapTime` по групуванню `Driver`) плюс
  графік довгих ранів (long runs) для аналізу темпу на паливі.
- `?drivers=` — використовувати для будь-якого фільтрованого вигляду
  (наприклад "показати лише топ-5 після кваліфікації").
- `TrackStatus` — код(и) стану траси на колі (жовті/червоні прапори,
  SC/VSC); потрібна власна мапа кодів → бейдж/іконка, бекенд віддає їх
  як рядок без розшифровки.
- `IsAccurate: false` — коло, яке FastF1 вважає невірогідним (аутлап,
  перерваний круг тощо) — варто приглушувати/фільтрувати в графіках
  темпу, інакше викиди спотворюють шкалу.

---

## 7. `GET /api/compare/{year}/{round}/{session}?drivers=A,B[,C...]` — порівняння пілотів

Мінімум 2 коди пілотів (інакше `400`). Відповідь — об'єкт, ключ = код
пілота:

```json
{
  "VER": {"laps": [ {LapNumber, LapTime, Sector1/2/3Time, Compound,
                      TyreLife, Stint, Position, IsPersonalBest}, ... ],
          "fastest_lap": { ...повне коло... } | null},
  "HAM": { ... }
}
```

**Потрібно на фронті (окрема сторінка/режим "Порівняння", раніше не існувала):**
- Мультиселект 2+ пілотів (джерело — `/api/drivers`, див. п. 4), кнопка
  "Порівняти".
- **Графік темпу по колах**: одна лінія на пілота, `LapNumber` (X) vs
  `LapTime` (Y) — по кольору команди/пілота з `TeamColor`.
- **Графік/таблиця відставання по колах**: рахується на фронті як
  кумулятивна різниця `LapTime` між обраними пілотами (бекенд її не
  віддає готовою).
- Порівняльна картка найшвидших кіл (`fastest_lap` кожного) side-by-side.
- Порівняння стратегій шин по обраних пілотах (той самий timeline, що
  в п. 5, але кілька смуг одна під одною) — компаунд для кожного кола
  бере з `laps[].Compound`/`Stint`, оскільки `compare` не повертає
  готові `stints`, на відміну від `/api/driver`.
- Явне повідомлення в UI, якщо викликати з 1 пілотом — не покладатись
  тільки на 400 від бекенду, валідувати кількість вибраних пілотів
  ще на клієнті перед запитом.

## 8. `GET /api/weather/{year}/{round}/{session}` — погода сесії

Масив точок:

```
Time (сек. від початку сесії), AirTemp, TrackTemp, Humidity,
Pressure, Rainfall (bool), WindDirection (град.), WindSpeed
```

**Потрібно на фронті:**
- Блок/сторінка "Погода" з двома-трьома лінійними графіками
  (AirTemp/TrackTemp по `Time`; Humidity окремо; Wind — можна
  роза вітрів або просто лінія швидкості).
- Індикатор дощу (`Rainfall`) — накладена область/іконка на графіку
  температури, щоб бачити, коли саме йшов дощ протягом сесії.
- Використати `Time` як вісь X разом з `laps[].Time` (розділ 6), щоб
  можна було зіставити зміну погоди з падінням темпу/піт-стопами —
  обидва поля в одній системі відліку (секунди від початку сесії).

## 9. `GET /api/predict/{year}/{round}` — передбачення (заглушка)

Відповідь: `[{predicted_position, driver, team, confidence: null}, ...]`.

**Потрібно на фронті:**
- Окремий блок/сторінка "Прогноз", що явно позначена як попередня
  (наприклад підпис "модель ще не підключена") — поки що
  `predicted_position` буквально дублює фактичний результат гонки,
  а `confidence` завжди `null`. Верстати UI під `confidence` (наприклад
  прогрес-бар "% впевненості") варто вже зараз, щоб не переробляти,
  коли на бекенді з'явиться реальна модель — просто закласти
  `confidence ?? "н/д"` в рендер.

## 10. `GET /api/seasons` — список сезонів (CSV, без мережі)

Відповідь — плаский масив років: `[1950, 1951, ..., 2025, 2026]`.

**Потрібно на фронті:**
- Джерело для **будь-якого селектора року** в застосунку (сторінка
  сезону, залік, форма вибору для порівняння) — замість хардкодженого
  діапазону `2018..2026`. Найстаріші сезони (1950-ті) можуть не мати
  повного набору даних у решті CSV-ендпоінтів нижче — трактувати як
  звичайний 404, не як помилку.
- На відміну від FastF1-ендпоінтів (розділ 0.5), цей запит завжди
  миттєвий (статичний файл у пам'яті бекенду) — не потребує
  skeleton/spinner, можна викликати ще до першого рендеру сторінки.

---

## 11. `GET /api/standings/drivers/{year}` та `GET /api/standings/constructors/{year}` — залік сезону (CSV)

Підсумковий залік станом на останній етап сезону в датасеті (не поточний
момент часу для сезонів, що ще тривають — дивись `/api/csv/results` нижче
для актуальніших даних по вже відбулись етапах).

Пілоти:

```json
[{"position": 1, "points": 575.0, "wins": 19, "driverId": 830,
  "code": "VER", "forename": "Max", "surname": "Verstappen",
  "nationality": "Dutch"}, ...]
```

Конструктори:

```json
[{"position": 1, "points": 860.0, "wins": 21, "constructorId": 9,
  "name": "Red Bull", "nationality": "Austrian"}, ...]
```

**Потрібно на фронті:**
- Сторінка "Чемпіонат {year}" з двома таблицями/табами: Пілоти /
  Конструктори, відсортовані за `position` (бекенд уже сортує, фронт
  не мусить).
- Раніше (див. колишню версію розділу 10 нижче) для такої таблиці
  довелось би робити N запитів по всіх етапах сезону і сумувати очки на
  фронті — тепер це один швидкий запит, N-запитний підхід більше не
  потрібен.
- `wins` — окрема колонка або бейдж "🏆 ×19".
- Клік на пілота/команду — сенс має вести на `/api/races/{year}`
  (розділ 1) для вибору конкретного етапу, бо детальні дані пілота
  прив'язані до `(year, round, session)`, а не до сезону в цілому.

## 12. `GET /api/csv/results/{year}/{round}/{session}` і `GET /api/csv/drivers/{year}/{round}/{session}` — легкі результати без мережі (CSV)

`session` ∈ `R`/`Race`, `Q`/`Qualifying`, `S`/`Sprint` (регістр не
важливий). Практики (`FP1`-`FP3`) сюди **не входять** — Ergast не веде
результатів практик, запит на них поверне `404`; для практик і надалі
`/api/laps` (FastF1, розділ 6).

⚠️ **Це не заміна `/api/results`/`/api/drivers`** (розділи 3-4) — менший
набір полів, без `TeamColor`/`HeadshotUrl`/`BroadcastName`/
`ClassifiedPosition`/`CountryCode`, бо їх немає у CSV-датасеті. Якщо
сторінка результатів уже побудована під контракт `/api/results` —
лишай її на FastF1, не переводь на цей ендпоінт заради самого переходу.

Гонка/спринт (`R`/`S`):

```json
[{"position": 1, "position_text": "1", "grid": 1, "points": 25.0,
  "laps": 57, "total_time": 5636.736, "time_display": "1:33:56.736",
  "fastest_lap": 44, "fastest_lap_time": 96.236, "fastest_lap_rank": 6,
  "fastest_lap_speed": 202.452, "status": "Finished",
  "driver_number": 33, "code": "VER", "full_name": "Max Verstappen",
  "nationality": "Dutch", "team": "Red Bull"}, ...]
```

(`fastest_lap_speed` є лише для `R`, у `S` цього поля Ergast не дає.)

Кваліфікація (`Q`):

```json
[{"position": 1, "q1": 91.295, "q2": 90.503, "q3": 89.708,
  "driver_number": 33, "code": "VER", "full_name": "Max Verstappen",
  "nationality": "Dutch", "team": "Red Bull"}, ...]
```

`/api/csv/drivers/...` — той самий список, звужений до
`driver_number, code, full_name, team, position, points`.

**Потрібно на фронті:**
- Опційний "легкий режим" сторінки результатів (наприклад перемикач
  "офлайн"/"швидко" чи фолбек, якщо FastF1-запит довго не відповідає) —
  ці ендпоінти завжди миттєві, без прогрітого кешу на першому запиті
  (розділ 0.5 тут не діє).
- `total_time` — це вже готовий загальний час у секундах (для лідера)
  чи повний час відстаючого пілота (не лише відставання) — на відміну
  від `time_display`, який дублює сирий рядок з датасету (`"+5.478"`
  для відстаючих) для показу як є, без перерахунку на фронті.
- Для `Q`: `q1`/`q2`/`q3` можуть бути `null`, якщо пілот вилетів на
  ранішому сегменті — рендерити прочерк, не `0:00.000`.
- `status` тут — вже розшифрований текст (`"Finished"`, `"Retired"`,
  `"Accident"` тощо) з `status.csv`, готовий для прямого показу.

## 13. `GET /api/csv/pitstops/{year}/{round}` — піт-стопи гонки (CSV, новий функціонал)

Функціонал, якого раніше в API не було взагалі.

```json
[{"driver_number": 10, "code": "GAS", "full_name": "Pierre Gasly",
  "stop": 1, "lap": 9, "time_of_day": "18:18:56", "duration": 25.885}, ...]
```

Відсортовано по `lap`, потім по `stop`. `duration` — секунди (float),
`time_of_day` — годинник доби, коли стався стоп (НЕ інтервал, не
конвертувати як тривалість).

**Потрібно на фронті (нова функціональність):**
- Таблиця/стрічка піт-стопів гонки: пілот, коло, тривалість — сортована
  за замовчуванням по колу (найзручніше для читання "що відбувалось по
  ходу гонки").
- Маркери піт-стопів на графіку темпу пілота (`/api/driver`, розділ 5,
  поле `laps[].PitInTime`/`PitOutTime` вже підказує **коли** був стоп) —
  цей ендпоінт додає точну **тривалість** самого стопу, якої FastF1-поля
  не дають напряму.
- Рейтинг "найшвидший піт-стоп гонки" — `min(duration)` по всіх записах,
  простий обчислюваний бейдж на сторінці етапу.
- Немає піт-стопів для дуже старих сезонів чи скасованих гонок — `404`,
  трактувати як "даних немає", не як помилку застосунку.

## 14. Чого бекенд **не** дає (і варто або не будувати, або порахувати на фронті)

- **Телеметрії** (швидкість/газ/гальмо по треку, зіставлення з картою
  кола) бекенд не віддає — тільки агреговані `SpeedI1/I2/FL/ST` на
  рівні кола. Секторна/поколова карта швидкості на фронті неможлива
  без розширення бекенду.
- **Дельти між пілотами** (скільки секунд позаду) не рахуються бекендом
  — тільки сирі `LapTime`/`Time`. Уся арифметика порівняння — на фронті.
- **Розшифровки кодів** (`TrackStatus`, `Status`, `ClassifiedPosition`)
  бекенд не надає — потрібні власні словники-мапи на фронті.

## 15. `GET /api/analysis/{year}/{round}?refresh=true` — аналіз прогнозу (реальна модель v2.0)

На відміну від `/api/predict` (розділ 9, все ще заглушка), це - робочий
двоетапний ансамбль (DNF-класифікатор + LambdaRank ranker + XGBoost
regressor), натренований на `data/*.csv`. Рахується **один раз на
етап**: перший запит будує прогноз і кешує його на диску бекенду,
всі наступні запити того самого `(year, round)` віддають той самий
збережений результат миттєво - навіть якщо надійшли нові дані. Додай
`?refresh=true`, щоб примусово перерахувати.

Відповідь:

```jsonc
{
  "race": { "year", "round", "race_id", "name", "date", "circuit_id" },
  "generated_at": "2026-08-24T15:20:51Z",
  "data": {
    "stage": "completed" | "post_quali" | "not_started",
    "source": "static_dataset" | "live_fastf1_quali" | "live_no_quali",
    "quali_available": true | false,
    "notes": ["...пояснення обмежень цього конкретного прогнозу..."]
  },
  "model": {
    "version": "v2.0",
    "best_alpha": 0.0,
    "metrics": { "mae_test", "top1", "podium_set", "top5_set", "top10_set",
                 "spearman_mean", "ndcg10", "dnf_auc_test", ... }
  },
  "predictions": [
    { "driver_id", "driver", "team", "grid", "quali_position",
      "predicted_position", "expected_position", "p_dnf",
      "actual_position": number | null, "hit": boolean | null }
  ],
  "feature_importance": {
    "ranker": [{ "feature", "label", "importance" }, ...],
    "dnf_classifier": [{ "feature", "label", "importance" }, ...]
  }
}
```

**Наповнення залежить від прогресу етапу** (`data.stage`/`data.source`) -
UI має явно показувати користувачу, на яких даних побудований саме цей
прогноз, а не подавати всі три випадки однаково:

- `completed` + `static_dataset` - етап уже давно в датасеті (є
  кваліфікація й результат). `actual_position`/`hit` заповнені для
  кожного пілота - є сенс UI з "прогноз vs факт" (як у розділі
  Predicted vs Actual).
- `completed` + `live_fastf1_quali` - етап реально вже проїхано, але в
  локальному CSV-датасеті ще нема (він оновлюється не в реальному
  часі) - кваліфікацію й фактичний результат бекенд підтягнув напряму з
  FastF1. Так само є `actual_position`/`hit`.
- `not_started`/`post_quali` + `live_no_quali`/`live_fastf1_quali` -
  етап ще не відбувся. `actual_position`/`hit` = `null` для всіх - UI
  не повинен малювати колонку "Факт" узагалі, лише прогноз. Якщо
  `quali_available=false` - склад пілотів і стартова решітка в
  `predictions[].grid`/`quali_position` - лише приблизні (взяті з
  останнього відомого етапу), про це й попереджає `data.notes[]`.
- `data.notes[]` - людські пояснення (українською) конкретних обмежень
  саме цього прогнозу (наприклад "кваліфікація ще недоступна") -
  показувати як попередження/тултіп над таблицею прогнозу, не
  ігнорувати.

**Потрібно на фронті:**
- Сторінка/блок "Аналіз прогнозу" для конкретного етапу (кнопка з
  картки етапу в календарі, розділ 1) - таблиця `predictions`,
  відсортована за `predicted_position`, з колонками Прогноз/Пілот/
  Команда/Квалі/P(DNF)/(Факт, якщо є).
- Бейдж стадії прогнозу на основі `data.stage` (наприклад "до
  кваліфікації" / "після кваліфікації" / "гонка завершена") і рендер
  `data.notes[]` як попередження під заголовком.
- Блок метрик моделі (`model.metrics`) - MAE/Top-N/Spearman/NDCG/DNF
  AUC - як загальна "візитка" якості моделі, однакова для всіх етапів
  (не перераховується щоразу, бере значення з тесту при тренуванні).
- `feature_importance.ranker`/`feature_importance.dnf_classifier` -
  готові пари `{label, importance}` для горизонтального bar chart
  (аналог "Top Features" з референс-скрипта) - `label` уже українською,
  не потрібен додатковий словник на фронті.
- Перший запит по новому етапу повільний (секунди - будує/тренує модель
  при першому зверненні бекенду за весь час його роботи, далі кеш) -
  той самий skeleton/spinner підхід, що й для FastF1-ендпоінтів
  (розділ 0.5), з ще більшим запасом за таймаутом.
- `404` з `{"detail": ...}` - етапу нема в календарі датасету (той
  самий контракт помилок, розділ 0.4).
